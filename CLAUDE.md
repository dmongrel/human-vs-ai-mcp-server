# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

An MCP (Model Context Protocol) server providing tooling to:
- Detect AI usage in text (estimate likelihood a given text was AI-generated), with an explainable per-signal breakdown.
- Offer recommendations to humanize AI-generated text.

Published on GitHub at [dmongrel/human-vs-ai-mcp-server](https://github.com/dmongrel/human-vs-ai-mcp-server) (`master` is the default and only branch); **not yet published to npm** (no version has been tagged/released — intentional until the tool set is stable) — see [README.md](./README.md) for install/usage and [TOOLS.md](./TOOLS.md) for the maintained tool reference.

## Commands

- Install: `npm install`
- Build: `npm run build` (runs `tsc`, emits to `dist/`)
- Run: `npm start` (runs `dist/index.js`; build first)
- Test: `npm test` (compiles `src` including `*.test.ts` files to `dist-test/` via `tsconfig.test.json`, then runs `node --test` against the compiled output). There is no lint config yet.

## Architecture

- TypeScript compiles from `src/` to `dist/` (see `tsconfig.json`: `commonjs` module, `es2016` target, `strict` mode, `outDir: dist`).
- `src/index.ts` is the entry point (shebang `#!/usr/bin/env node`, also wired as the `bin` target in `package.json`): constructs an `McpServer`, registers tools with `server.registerTool(name, { title, description, inputSchema }, handler)` using `zod` schemas, then connects a `StdioServerTransport`. Tool `description` fields are kept short by design — detailed usage docs live behind the `get_context` tool instead (see `src/context.ts`), so keep new tools' descriptions terse and put the real explanation in `CONTEXT`.
- `src/lib/detectAiUsage.ts` — thin orchestrator, `async`. Builds a `DetectorContext` (trimmed text, sentences, paragraphs, words, lowercased text, ruleset type), calls every `enabled` detector from `getDetectors()` (`src/lib/detectors/index.ts`), attaches each result's weight via `detector.weight(type)`, and combines them via weighted average into a 0-100 score. Re-exports `DocumentType` from `src/lib/detectors/types.ts` for backward-compat imports. Contains no detector logic itself — see `src/lib/detectors/` below.
- `src/lib/detectors/` — one file per detection signal, each implementing the shared `Detector` interface (`types.ts`: `id`, `name`, `enabled`, `weight(type)`, `run(ctx)`). `run()` returns `{ name, score, detail }` (no `weight` — the orchestrator attaches that) or `null` to omit the signal entirely (e.g. not enough text, or an unreachable optional backend). Each detector owns its own per-genre weight table and any calibration thresholds it needs (e.g. `markdownInProse.ts`'s `DENSITY_SATURATION`, `emDash.ts`'s `PER_1000_SATURATION`) — there is no more shared `WEIGHT_PROFILES` table. Built-in detectors: `burstiness.ts`, `lexicalDiversity.ts`, `aiPhrase.ts`, `readabilityUniformity.ts`, `markdownInProse.ts`, `emDash.ts`, `ngramRepetition.ts` (trigram diversity), `paragraphCoherence.ts` (adjacent-paragraph content-word cosine similarity, now `enabled: false` -- its premise was measured and does not hold for narrative prose; see the file header), `modelPerplexity.ts` (see below, currently `enabled: false`), and `llamaEnginePerplexity.ts` (see below, enabled but inert unless `LLAMA_ENGINE_MODEL_PATH` is set). Add a built-in signal by adding one file here and one line in `index.ts`'s `CORE_DETECTORS` array; nothing else needs to change. Research references are cited in comments at the top of each file. `index.ts`'s `getDetectors()` returns `CORE_DETECTORS` plus any plugins found via `loadPlugins()` (see next entry) — it re-scans `PLUGINS_DIR` on every call, so plugin files can be added/edited without restarting the server.
- `src/lib/detectors/loadPlugins.ts` — external, third-party plugin loading. Opt-in via the `PLUGINS_DIR` env var (unset by default — no behavior change for anyone not using this). Scans the directory for `.js` files and `require()`s each one, expecting a `Detector`-shaped export (`module.exports.detector`, `.default`, or the bare export) — plugins must be plain **CommonJS `.js`**, not TypeScript, since there's no bundled compiler to compile them at runtime (adding one would violate the minimal-dependencies convention). Fails open per file, logging to `console.error` (stderr — never stdout, since this is an MCP server using stdio for the protocol) and skipping: missing/unreadable directory, a file that throws on `require()`, a malformed export, or an `id` collision with an existing detector.
- `src/lib/detectors/modelPerplexity.ts` — the optional model-runner-based perplexity detector, calls `scorePerplexity` from `../modelRunner.js`. **Disabled via `enabled: false`** on the exported `Detector` object — the orchestrator filters on `enabled` before calling `run()`, so this never attempts a network call regardless of `MODEL_RUNNER_URL`. **Do not flip this to `true`** without re-reading the investigation in README.md's "Model runner (currently disabled)" section first: the technique was found structurally biased (near-zero perplexity for any successfully-reproduced text, regardless of content — not a fixable calibration issue) and impractically slow on every runner tested.
- `src/lib/modelRunner.ts` — optional client for a local, OpenAI-compatible model runner (LM Studio, Ollama, etc.), kept as groundwork for `detectors/modelPerplexity.ts` (currently disabled, see above) in case a better scoring technique or runner support emerges later — not currently exercised in production. `getModelRunnerUrl()` reads `MODEL_RUNNER_URL`; `scorePerplexity()` chunks the *whole* input text (not sampled) to fit context windows, scores each chunk, and averages token log-probabilities into a perplexity value — respecting an overall `MODEL_RUNNER_TIMEOUT_MS` time budget (default 60s; generation-based scoring is slow) by stopping further chunk requests once exceeded and averaging whatever completed. Follows the exact fail-open convention as `checkUpdate.ts`: any network/parse/shape error collapses to `null`, never throws. **Technique**: direct `/v1/completions` with `echo:true, logprobs:1` was tested against real LM Studio and Ollama instances and found non-functional on both (always returns `logprobs: null`, regardless of parameters). Instead uses a verbatim-echo technique via `/v1/chat/completions` — the model is asked to repeat each chunk back verbatim, and logprobs are read off its own reproduction; a Levenshtein-based similarity check (`MIN_SIMILARITY_RATIO`, 0.9) discards the chunk if the reproduction diverges too far. This mechanically works (verified with `meta-llama-3-8b-instruct`, a Gutenberg-AI-detection fine-tune, and `llama3.1:8b` on Ollama — exact-match reproductions, real logprobs) but is disabled anyway: greedy (temperature 0) decoding — required for the similarity check to pass — makes the model's own reproduction near-certain by construction, so the perplexity signal doesn't discriminate between inputs at all; three differently-worded human-written chapters all returned the identical result in testing. Optional `MODEL_RUNNER_MODEL` env var pins a specific model instead of using the first one `GET /v1/models` returns. Optional `MODEL_RUNNER_CONTEXT_TOKENS` env var sizes chunks against the model's actual context window — note this can make timeouts *more* likely on slow runners, since larger chunks take proportionally longer to generate.
- `src/lib/detectors/llamaEnginePerplexity.ts` — the bundled-engine perplexity detector, calls `scorePerplexityViaEngine` from `../llamaEngine.js`. **Enabled** (unlike `modelPerplexity.ts`): the technique is sound — real teacher-forced scoring, no generation step, no greedy-decoding bias, verified to discriminate across ~3 orders of magnitude on real text. Being enabled is free when unconfigured: `run()` returns `null` immediately unless `LLAMA_ENGINE_MODEL_PATH` is set, so no subprocess is spawned. The perplexity→score anchors do rest on a thin sample (n=3 per group, one author each, measured against `Qwen2.5-1.5B-Instruct.Q4_K_M` — see `docs/superpowers/notes/2026-07-25-llama-engine-calibration.md`). Widening that corpus is the main outstanding work, and any change of model requires re-measuring, since perplexity values don't transfer between models — see README.md's "Bundled engine perplexity".
- `src/lib/llamaEngine.ts` — client for the bundled llama.cpp-engine helper. Spawns `llama-engine-helper.exe` as a one-shot subprocess (JSON request on stdin, one JSON response line on stdout), enforces `LLAMA_ENGINE_TIMEOUT_MS`, and fails open to `null` on any spawn/exit/parse/shape error — same convention as `modelRunner.ts` and `checkUpdate.ts`. Activated by `LLAMA_ENGINE_MODEL_PATH` (plus optional `LLAMA_ENGINE_CTX_SIZE`, `LLAMA_ENGINE_TIMEOUT_MS`, and `LLAMA_ENGINE_HELPER_PATH` for local development). Resolves the helper from the `human-vs-ai-mcp-server-<platform>-<arch>` optional dependency, so adding platforms needs no code change here. Exports `_internals.spawn` purely as a test injection point — `node:child_process` members are getter-only and can't be monkeypatched the way `modelRunner.test.ts` patches `globalThis.fetch`.
- `native/llama-engine/` — Go source for that helper (`main.go` JSON contract, `scoring.go` pure perplexity math, `llama.go` the purego binding to `libllama`). Built via `npm run build:native` into `packages/win32-x64/`; a TypeScript-only contributor never needs a Go toolchain. `go test` covers chunking/scoring against canned logits; the real-model smoke test skips unless `LLAMA_ENGINE_TEST_MODEL` and `LLAMA_ENGINE_LIB_DIR` are both set. See `native/llama-engine/PLATFORMS.md` before touching anything platform-related.
- `src/lib/humanizeText.ts` — builds actionable `{ issue, suggestion, evidence }` recommendations on top of the same signals; does not rewrite text itself. `async` (awaits `detectAiUsage`). Also accepts the same `type` and `ignoreMd` parameters as `detectAiUsage`; `type` maps through `HUMANIZE_PROFILES` to per-check thresholds (e.g. `strategic` skips the markdown recommendation entirely; `creative` tolerates more em dashes/readability drift). When calling both tools on the same text, pass the same `type`/`ignoreMd` to each for consistent results. Its model-perplexity recommendation reads the score off `detection.detectors` (already computed by the `detectAiUsage` call it makes internally) rather than calling `scorePerplexity` a second time — do not change this to an independent call, it would duplicate an expensive network request.
- `src/lib/aiPhrases.ts` — the list of known LLM stock phrases used by the phrase-frequency detector; extend this list as new "AI tells" are documented.
- `src/lib/text.ts` — hand-written tokenization/statistics helpers (sentence/paragraph splitting, syllable counting, mean/stdev, `stripMarkdownMarkup`, `fleschReadingEase`). Deliberately dependency-free per project convention — prefer writing small routines here over adding an npm package. `fleschReadingEase` lives here (not in a detector file) since both `readabilityUniformity.ts` and `humanizeText.ts` use it.
- `src/lib/io.ts` — shared input/output handling for tools: `resolveInputText` accepts either `text` or `filePath` (exactly one required); `deliverOutput` returns content inline or writes it to `reportPath` if given, creating directories as needed.
- `src/context.ts` — the `CONTEXT` map backing the `get_context` tool. Keep this in sync with `TOOLS.md` when tool behavior changes. Also holds `setUpdateNotice`/an in-memory `_updateNotice` that, if set, gets prepended to `get_context`'s output.
- `src/lib/checkUpdate.ts` — on server start, checks `registry.npmjs.org` for a newer published version than the local `package.json` version (fails open/silently on any network or parse error) and, if the check somehow finds one before the project has ever been published, calls `setUpdateNotice`. Currently a no-op in practice since nothing is published yet.
- `src/lib/**/*.test.ts` — tests colocated with the modules they cover, using Node's built-in `node:test`/`node:assert` (no test framework dependency). `tsconfig.json` excludes `*.test.ts` from the publish build; `tsconfig.test.json` includes them and outputs to `dist-test/` for `npm test`. Running `node --test` directly against a *directory* has been observed to hang on Windows — the `test` script instead passes an explicit glob (`dist-test/**/*.test.js`), which is reliable; keep that pattern if editing the script. `modelRunner.test.ts` and the model-perplexity tests in `detectAiUsage.test.ts`/`humanizeText.test.ts` stub `globalThis.fetch` directly (no real network calls) — follow that pattern for any future model-runner-adjacent tests rather than hitting a real server. `src/lib/detectors/loadPlugins.test.ts` exercises the plugin loader against real temp-directory fixtures (`fs.mkdtempSync`), since it's genuinely testing filesystem/`require()` behavior, not something worth mocking.
- `examples/` — three `.md` fixtures of creative prose used for manually exercising the detection/humanization tools against realistic long-form text (not wired into the automated test suite).

## Conventions

- Keep runtime dependencies minimal (currently just `@modelcontextprotocol/sdk` and `zod`). Prefer hand-written implementations for small routines over adding a new package. This is about **npm packages specifically** (supply-chain/attack-surface risk — packages can go offline, get compromised, or ship malicious updates), not about network calls in general — `checkUpdate.ts` and the optional `modelRunner.ts` both make network calls without adding any new npm dependency, and that's fine.
- The optional model-runner detector (`src/lib/modelRunner.ts`) is activated via the `MODEL_RUNNER_URL` env var (plus optional `MODEL_RUNNER_MODEL`, `MODEL_RUNNER_TIMEOUT_MS`, `MODEL_RUNNER_CONTEXT_TOKENS`), set in `.mcp.json`'s `env` block — not a tool parameter. It's opt-in, localhost-only by convention, and fails open; do not make it required or change activation to a per-call parameter without discussion. It's also currently disabled regardless of this env var — see `src/lib/detectors/modelPerplexity.ts`.
- External detector plugins (`src/lib/detectors/loadPlugins.ts`) are activated via the `PLUGINS_DIR` env var, same pattern as `MODEL_RUNNER_URL` above — opt-in, unset by default, env-var-activated rather than a tool parameter. Plugins are plain CommonJS `.js` files, not TypeScript (no bundled compiler to compile them at runtime), and run with full in-process trust (no sandboxing) — document this clearly to users, don't add a false sense of safety.
- The bundled llama.cpp engine pins llama.cpp release **`b10107`** in `native/llama-engine/build-win32-x64.ps1`. This is load-bearing, not incidental: `llama.go` reads struct field offsets from that exact release's `include/llama.h`, and it passes struct-by-value arguments as raw pointers, which is valid only under the Microsoft x64 calling convention. Bumping the release means re-verifying the offsets; adding a non-Windows platform means revisiting the ABI approach entirely — see `native/llama-engine/PLATFORMS.md`.
- Prebuilt native binaries ship in per-platform npm packages under `packages/`, referenced from `optionalDependencies` at an exact version that moves in lockstep with the main package. These are first-party and don't count against the minimal-npm-dependencies convention, which is about third-party supply-chain risk; Go module dependencies (`purego`) likewise aren't npm dependencies.
- `package.json` is set up npm-publish-style (`bin`, `files`, `prepublishOnly`, `private: false`) and registry update-checking exists (`src/lib/checkUpdate.ts`), but the project has **not been published or version-tagged** — that's intentional until the tool set is considered stable. Do not run `npm publish` or tag a release without explicit instruction.
- Update `TOOLS.md` and `src/context.ts` together whenever a tool's inputs, outputs, or behavior change.
