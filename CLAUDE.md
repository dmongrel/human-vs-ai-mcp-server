# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

An MCP (Model Context Protocol) server providing tooling to:
- Detect AI usage in text (estimate likelihood a given text was AI-generated), with an explainable per-signal breakdown.
- Offer recommendations to humanize AI-generated text.

Published on GitHub at [dmongrel/human-vs-ai-mcp-server](https://github.com/dmongrel/human-vs-ai-mcp-server) (`master` is the default and only branch); **not yet published to npm** (no version has been tagged/released — intentional until the tool set is stable) — see [README.md](./README.md) for install/usage and [TOOLS.md](./TOOLS.md) for the maintained tool reference.

## Commands

- Install: `npm install`
- Build: `npm run build` (runs `tsc`, emits to `dist/`)
- Run: `npm start` (runs `dist/index.js`; build first)
- Test: `npm test` (compiles `src` including `*.test.ts` files to `dist-test/` via `tsconfig.test.json`, then runs `node --test` against the compiled output). There is no lint config yet.

## Architecture

- TypeScript compiles from `src/` to `dist/` (see `tsconfig.json`: `commonjs` module, `es2016` target, `strict` mode, `outDir: dist`).
- `src/index.ts` is the entry point (shebang `#!/usr/bin/env node`, also wired as the `bin` target in `package.json`): constructs an `McpServer`, registers tools with `server.registerTool(name, { title, description, inputSchema }, handler)` using `zod` schemas, then connects a `StdioServerTransport`. Tool `description` fields are kept short by design — detailed usage docs live behind the `get_context` tool instead (see `src/context.ts`), so keep new tools' descriptions terse and put the real explanation in `CONTEXT`.
- `src/lib/detectAiUsage.ts` — the heuristic AI-detection engine, `async` (it awaits the optional 7th detector). Each signal (sentence-length burstiness, lexical diversity, AI stock-phrase frequency, readability uniformity, markdown-in-prose artifacts, em dash overuse) is an isolated function returned in a `detectors` array and combined via weighted average into a 0-100 score. Add new signals by adding one function + one array entry; nothing else needs to change. Research references are cited in comments at the top of the file. An optional `type: "creative" | "strategic"` parameter selects a `WEIGHT_PROFILES` entry that reweights the signals and adjusts markdown/em-dash saturation thresholds for that genre (see comments above `WEIGHT_PROFILES`); omit it for the genre-agnostic `default` profile. An optional `ignoreMd` boolean strips literal `*`/`_`/`#` characters (via `stripMarkdownMarkup` in `text.ts`) before analysis, neutralizing the markdown detector's header/bold counts without affecting `-` bullet lines. A 7th detector, `modelPerplexityDetector`, calls `scorePerplexity` from `modelRunner.ts`; it's `async` and returns `null` (omitted from `detectors`, not included with a neutral score) whenever `MODEL_RUNNER_URL` is unset or the call fails — activation is via that env var, not a tool parameter, so its weight (`profile.modelPerplexity`, flat 15% across all profiles, additive on top of the other six unchanged weights) only affects the score when configured.
- `src/lib/modelRunner.ts` — optional client for a local, OpenAI-compatible model runner (LM Studio, Ollama, etc.), used only by `modelPerplexityDetector`. `getModelRunnerUrl()` reads `MODEL_RUNNER_URL`; `scorePerplexity()` chunks the *whole* input text (not sampled) to fit context windows, scores each chunk, and averages token log-probabilities into a perplexity value — respecting an overall `MODEL_RUNNER_TIMEOUT_MS` time budget (default 60s; generation-based scoring is slow) by stopping further chunk requests once exceeded and averaging whatever completed. Follows the exact fail-open convention as `checkUpdate.ts`: any network/parse/shape error collapses to `null`, never throws. **Technique**: direct `/v1/completions` with `echo:true, logprobs:1` was tested against a real LM Studio instance and found non-functional (always returns `logprobs: null`, regardless of parameters). Instead uses a verbatim-echo technique via `/v1/chat/completions` — the model is asked to repeat each chunk back verbatim, and logprobs are read off its own reproduction; a Levenshtein-based similarity check (`MIN_SIMILARITY_RATIO`, 0.9) discards the chunk if the reproduction diverges too far, so a bad echo never produces a misleading score. This makes model choice matter: verified working with `meta-llama-3-8b-instruct` and a Gutenberg-AI-detection fine-tune; fails with models that don't follow verbatim-repetition instructions (e.g. `qwen2.5-0.5b-instruct`) or that route through an internal reasoning/"thinking" step before real output (e.g. `qwen3.6-35b-a3b-mtp`, `google/gemma-4-12b-qat`) — those cases still fail open cleanly, just with the signal omitted. Optional `MODEL_RUNNER_MODEL` env var pins a specific model instead of using the first one `GET /v1/models` returns (useful with several models loaded at once). Optional `MODEL_RUNNER_CONTEXT_TOKENS` env var sizes chunks against the model's actual context window (larger/fewer chunks) instead of the conservative built-in default — not required for correctness, just efficiency.
- `src/lib/humanizeText.ts` — builds actionable `{ issue, suggestion, evidence }` recommendations on top of the same signals; does not rewrite text itself. `async` (awaits `detectAiUsage`). Also accepts the same `type` and `ignoreMd` parameters as `detectAiUsage`; `type` maps through `HUMANIZE_PROFILES` to per-check thresholds (e.g. `strategic` skips the markdown recommendation entirely; `creative` tolerates more em dashes/readability drift). When calling both tools on the same text, pass the same `type`/`ignoreMd` to each for consistent results. Its model-perplexity recommendation reads the score off `detection.detectors` (already computed by the `detectAiUsage` call it makes internally) rather than calling `scorePerplexity` a second time — do not change this to an independent call, it would duplicate an expensive network request.
- `src/lib/aiPhrases.ts` — the list of known LLM stock phrases used by the phrase-frequency detector; extend this list as new "AI tells" are documented.
- `src/lib/text.ts` — hand-written tokenization/statistics helpers (sentence/paragraph splitting, syllable counting, mean/stdev, `stripMarkdownMarkup`). Deliberately dependency-free per project convention — prefer writing small routines here over adding an npm package.
- `src/lib/io.ts` — shared input/output handling for tools: `resolveInputText` accepts either `text` or `filePath` (exactly one required); `deliverOutput` returns content inline or writes it to `reportPath` if given, creating directories as needed.
- `src/context.ts` — the `CONTEXT` map backing the `get_context` tool. Keep this in sync with `TOOLS.md` when tool behavior changes. Also holds `setUpdateNotice`/an in-memory `_updateNotice` that, if set, gets prepended to `get_context`'s output.
- `src/lib/checkUpdate.ts` — on server start, checks `registry.npmjs.org` for a newer published version than the local `package.json` version (fails open/silently on any network or parse error) and, if the check somehow finds one before the project has ever been published, calls `setUpdateNotice`. Currently a no-op in practice since nothing is published yet.
- `src/lib/*.test.ts` — tests colocated with the modules they cover, using Node's built-in `node:test`/`node:assert` (no test framework dependency). `tsconfig.json` excludes `*.test.ts` from the publish build; `tsconfig.test.json` includes them and outputs to `dist-test/` for `npm test`. Running `node --test` directly against a *directory* has been observed to hang on Windows — the `test` script instead passes an explicit glob (`dist-test/**/*.test.js`), which is reliable; keep that pattern if editing the script. `modelRunner.test.ts` and the model-perplexity tests in `detectAiUsage.test.ts`/`humanizeText.test.ts` stub `globalThis.fetch` directly (no real network calls) — follow that pattern for any future model-runner-adjacent tests rather than hitting a real server.
- `examples/` — three `.md` fixtures of creative prose used for manually exercising the detection/humanization tools against realistic long-form text (not wired into the automated test suite).

## Conventions

- Keep runtime dependencies minimal (currently just `@modelcontextprotocol/sdk` and `zod`). Prefer hand-written implementations for small routines over adding a new package. This is about **npm packages specifically** (supply-chain/attack-surface risk — packages can go offline, get compromised, or ship malicious updates), not about network calls in general — `checkUpdate.ts` and the optional `modelRunner.ts` both make network calls without adding any new npm dependency, and that's fine.
- The optional model-runner detector (`src/lib/modelRunner.ts`) is activated via the `MODEL_RUNNER_URL` env var (plus optional `MODEL_RUNNER_MODEL`, `MODEL_RUNNER_TIMEOUT_MS`, `MODEL_RUNNER_CONTEXT_TOKENS`), set in `.mcp.json`'s `env` block — not a tool parameter. It's opt-in, localhost-only by convention, and fails open; do not make it required or change activation to a per-call parameter without discussion.
- `package.json` is set up npm-publish-style (`bin`, `files`, `prepublishOnly`, `private: false`) and registry update-checking exists (`src/lib/checkUpdate.ts`), but the project has **not been published or version-tagged** — that's intentional until the tool set is considered stable. Do not run `npm publish` or tag a release without explicit instruction.
- Update `TOOLS.md` and `src/context.ts` together whenever a tool's inputs, outputs, or behavior change.
